# 웹·모바일 앱 통합 및 병합 에이전트 프롬프트

아래 내용을 웹·백엔드 번들과 모바일 앱 저장소를 함께 받은 에이전트에게 그대로 전달하세요.

---

당신은 JupJup의 기존 웹 프론트, 백엔드, 모바일 앱을 실제로 통합하고 대상 브랜치에 병합하는 담당 에이전트다. 첨부된 `jupjup-web-backend-mobile-integration-df63422.zip`을 풀고 다음 순서로 읽어라.

1. `deliverables/WEB_APP_INTEGRATION_HANDOFF.md`
2. `deliverables/MOBILE_APP_HANDOFF.md`
3. `specs/app_api_openapi.json`
4. `specs/mobile_backend_contract_matrix.json`
5. `frontend/README.md`, 루트 `README.md`
6. 작업 대상 모바일 앱 저장소의 `README`, `AGENTS.md`, `CLAUDE.md`, 패키지 설정

번들 구조에서 `frontend/`는 기존 React/Vite 웹이고 `src/jupjup/`는 Python 백엔드다. 모바일 앱 소스는 별도로 제공된 작업 저장소에 있다. 세 프로젝트를 하나의 폴더로 억지로 합치지 말고, 현재 저장소 구조와 배포 단위를 보존하면서 동일 백엔드에 연결하라.

최종 목표:

- 기존 웹의 `/v1` 로그인/OAuth, 콘텐츠 저장, 분석, 목록, 상세, 검색 흐름을 깨뜨리지 않는다.
- 모바일 앱은 동결된 `/api` OpenAPI 계약만 사용한다.
- 모바일에서 저장한 URL이 백엔드 브리지를 통해 웹 콘텐츠와 AI 분석 작업으로 생성되고, 양쪽 화면에서 분석 상태와 결과를 확인할 수 있게 한다.
- mock/demo/local-only 앱 저장 계층을 실제 서버 연동으로 교체한다.

작업 규칙:

- 시작 전 모든 저장소의 브랜치, remote, dirty 파일을 확인하고 사용자 변경을 보존한다.
- 번들의 웹 소스에는 전달 시점의 로컬 변경도 포함되어 있으므로, 대상 웹 저장소와 비교 후 의미 단위로 병합한다. 파일 전체 덮어쓰기를 피한다.
- `specs/app_api_openapi.json`을 모바일 계약의 유일한 기준으로 사용한다.
- 모바일은 `/api`, 웹은 기존 `/v1` 경계를 유지한다. 클라이언트끼리 DTO를 잘못 공유하지 않는다.
- 백엔드의 앱 콘텐츠 브리지를 우회하거나 앱에서 웹 DB 구조를 직접 가정하지 않는다.
- 실제 `.env`, OAuth secret, 토큰, 로컬 IP를 커밋하지 않는다.
- force push, reset --hard, 사용자 파일 삭제를 하지 않는다.

모바일 구현 필수사항:

- 저장소 관례에 맞는 typed API client를 구현하고 환경별 base URL을 분리한다.
- 회원가입, 로그인, 로그아웃, 세션 복원, 내 정보 API를 연결한다.
- Bearer 토큰을 Keychain/Keystore 등 보안 저장소에 보관하고 로그에 출력하지 않는다.
- POST/PATCH는 JSON으로 보내고 bodyless POST도 `{}`를 보낸다.
- 401에는 세션 제거와 로그인 이동, `409 DUPLICATE_CONTENT`에는 중복 안내를 제공한다.
- 콘텐츠 CRUD, 복원, 휴지통 비우기, 알림, 검색 기록을 실제 API에 연결한다.
- 저장 후 분석 중/완료/실패 상태를 표시하고, 쓰기 완료 및 foreground 복귀 시 `/state`를 갱신한다.
- 로딩, 빈 상태, 재시도 가능한 네트워크 오류를 UI에 반영한다.

웹 통합 필수사항:

- 번들의 `frontend/src`와 대상 웹 브랜치를 비교해 누락된 최신 UI 변경을 병합한다.
- 웹 API base URL과 OAuth public origin 설정을 환경 변수로 유지한다.
- 로그인 사용자별 콘텐츠·즐겨찾기·검색 상태의 계정 격리를 유지한다.
- 저장 상세 화면에서 실제 백엔드 분석 단계와 실패/재시도 상태가 보이는지 확인한다.
- 앱에서 생성한 URL 콘텐츠가 웹 목록·상세·검색에 나타나는지 실제 서버로 확인한다.
- 기존 디자인 시스템, 라우팅, 반응형 레이아웃을 보존한다.

검증은 빠르되 핵심 흐름을 실제로 확인한다.

1. 백엔드: 앱 계약·브리지 집중 테스트와 typecheck/lint를 실행한다.
2. 웹: typecheck, 핵심 integration test, production build를 실행한다.
3. 앱: API client의 성공/401/409/네트워크 오류 테스트를 실행한다.
4. 실제 서버에서 앱 로그인 → URL 저장 → 분석 상태 갱신을 확인한다.
5. 같은 콘텐츠가 웹 목록 → 상세 → 검색에서 보이는지 확인한다.
6. 앱 삭제/복원 결과가 웹과 모순되지 않는지 확인한다.

병합 방식:

- 변경을 가능하면 `backend contract`, `mobile integration`, `web sync` 단위 커밋으로 나눈다.
- 충돌은 양쪽 기능을 이해한 뒤 해결하고 사용자 변경을 보존한다.
- 핵심 테스트가 통과하면 요청된 통합 브랜치에 병합하고 remote에 push한다.
- 점수 산정이나 장시간 선택 테스트에 시간을 낭비하지 말고, 실패 시 사용자 핵심 흐름을 막는 문제부터 수정한다.

최종 보고:

- 웹·백엔드·앱 각각의 최종 브랜치와 커밋
- 병합·push 여부
- 실제로 확인한 end-to-end 흐름
- 실행한 테스트와 결과
- 실기기/에뮬레이터 확인 환경
- 운영 배포에 남은 외부 값(도메인, HTTPS 인증서 등)
- 미완료 항목과 정확한 다음 조치

선택적인 질문 때문에 멈추지 말고 저장소 관례와 동결 명세를 기준으로 합리적인 기본값을 선택해 구현·검증·병합까지 끝내라. 운영 도메인이나 인증서처럼 제공받지 못한 외부 값만 명확한 blocker로 남겨라.
